Terraform Does Not Make You DevOps

The same infrastructure-as-code engine can support a ticket queue or a platform operating model. A valid plan explains what may change. It does not show whether teams can change it safely.

A green plan answers a smaller question

An authenticated Terraform plan is useful evidence. It shows that Terraform and its providers can evaluate a proposed configuration against the selected target. It does not prove that Azure deployed the resources, that production approval is well designed, that telemetry reaches an owner, or that recovery has been rehearsed.

That gap sits behind one of the questions I hear most often from cloud engineers: “Will learning Terraform make me a DevOps engineer?”

My honest answer is: not necessarily.

This is not a comparison of seniority, capability, or job titles. A cloud engineer can work with a mature DevSecOps mindset. Someone titled “DevOps Engineer” can still preserve ticket queues, one-time provisioning, and manual handoffs. The comparison is between operating models.

Terraform can execute an infrastructure decision. It cannot supply the operating model that makes the decision safe, repeatable, observable, and owned.

Terraform is valuable engineering machinery. It builds a dependency graph, compares desired and current state, produces a plan, and executes approved changes. But it cannot decide how teams should consume infrastructure, which risks require approval, who owns a service after deployment, what signals define health, or how the organization learns from failure.

Terragrunt does not automatically supply that operating model either. It can help centralize state and configuration conventions. The DevOps value still comes from the decisions encoded around it.

Three questions define the engineering scope

Before selecting a tool, separate the work into three questions. Each one expands the definition of success.

1

What must exist in Azure?

Resources, topology, identity boundaries, secure defaults, and the relationships between them.

2

How can teams change it safely?

Consumer interfaces, state boundaries, review, promotion, approval, and an auditable path to production.

3

How does control persist?

Policy, telemetry, ownership, drift response, recovery, cost, and evidence throughout the lifecycle.

Terraform can encode decisions across all three questions, especially the desired infrastructure state. Terragrunt can help compose those decisions across environments and state boundaries. Neither tool chooses acceptable risk, assigns ownership, grants approval authority, or closes the feedback loop. Those are engineering and organizational decisions.

Evidence status for this article

The Azure state backend was applied and observed in an isolated non-production subscription. Both workload paths completed authenticated Azure plans. Their workload applies and teardown lifecycle have not been observed, so this article does not claim that they have.

One module, two operating contracts

To make the comparison concrete, I built one reusable Terraform module and consumed it in two different ways. Both paths use the same Azure provider versions and the same secure core: a resource group, virtual network, subnet, network security group, private storage account, private endpoint, and private DNS.

That common baseline matters. The left side is not intentionally insecure just to make the platform side look good. The illustration makes the configured operating-capability delta visible.

Treat Terragrunt here as the composition layer, not the cause. Direct Terraform can encode the complete platform contract, while Terragrunt can also support a request-oriented model. I use it here because it makes the state and environment contract explicit.

The direct Terraform path: secure plan, incomplete operating contract

The direct root calls the shared module and deliberately makes its lifecycle omissions visible: 

module "workload_foundation" {
  source = "../modules/workload-foundation"

  operating_model      = "ticket-driven"
  enable_observability = false
  enable_recovery      = false
  enable_delete_lock   = false

  tags = {
    delivery_path = "manual-request"
    state_model    = "local"
  }
}

This path is not “bad Terraform.” Its authenticated plan still proposed a private, keyless storage account with a default-deny firewall, a private endpoint, private DNS, and a protected network foundation.

What it does not define is just as important: there is no shared remote state contract, observability sink, diagnostic route, recovery policy, or deletion protection. The configuration does not specify how those concerns will be delivered or owned; they require an additional change or workflow. The plan reflected the provisioning request exactly as configured.

The Terragrunt path: an explicit platform contract

The Terragrunt path consumes the same module, but it makes the operating decision explicit in version-controlled environment configuration: 

inputs = {
  operating_model      = "devops-platform"
  enable_observability = true
  enable_recovery      = true
  enable_delete_lock   = true
  lifecycle_phase      = local.environment_config.locals.lifecycle_phase

  tags = {
    delivery_path = "reviewed-terragrunt"
    state_model    = "remote-azure-blob"
    service_tier   = "platform-foundation"
  }
}

Its root configuration generates an Azure backend with a state key based on the environment path and requires Microsoft Entra authorization: 

remote_state {
  backend = "azurerm"

  config = {
    resource_group_name  = local.state_resource_group
    storage_account_name = local.state_storage_account
    container_name       = local.state_container
    key                  = "${path_relative_to_include()}/terraform.tfstate"
    subscription_id      = local.subscription_id
    use_azuread_auth     = true
  }
}

In the Azure validation run, Terragrunt initialized successfully while storage shared-key access was disabled. It created the expected remote state object at live/dev/foundation/terraform.tfstate. That is direct evidence that this state path used the intended keyless authorization model.

What changed in the plan?

The direct Terraform plan proposed 10 resources. The Terragrunt platform plan proposed 14. Resource count is not a measure of DevOps maturity, but the delta exposes four concrete operating capabilities: Log Analytics, Application Insights, NSG diagnostic settings, and a resource-group management lock.

DevOps value is the controlled path through change

Adding Log Analytics or a lock does not, by itself, make a team DevOps. The larger value is the delivery path those controls participate in:

This loop is a target operating model, not a claim that the current lab executes every stage. The repository demonstrates the module contract, local checks, saved planning, and keyless backend state. It does not yet contain an example-specific pull-request policy gate or a live drift-remediation exercise.

1. A product contract instead of a ticket response

The cloud resource is not the finished product. Teams consume a documented capability with inputs, outputs, defaults, and ownership. They do not need to rediscover the implementation through a sequence of infrastructure tickets.

2. Reviewable change instead of one-time execution

A plan becomes evidence tied to a source revision and a target. Tests, security checks, and human approval can reason about the exact proposed change before it reaches production.

3. Guardrails that fail closed

A production requirement must block an unsafe plan, not merely print a warning. The module therefore uses a resource lifecycle precondition: 

lifecycle {
  precondition {
    condition = var.environment != "prod" || (
      var.operating_model == "devops-platform" &&
      var.enable_observability &&
      var.enable_recovery &&
      var.enable_delete_lock
    )
    error_message = "Production requires the complete platform contract."
  }
}

4. Feedback instead of handoff

Provisioning creates resources. Operation establishes whether they are healthy, who responds, which telemetry matters, and how a failure changes the next version of the platform contract.

5. Recovery and teardown as designed workflows

Recovery is not an optimistic statement in a runbook. It is encoded in versioning and retention settings, then should be verified through tests and live exercises. The live recovery exercise for this article remains pending. Deletion protection is paired with an explicit teardown phase so that safety does not make cleanup an improvised exception.

Before calling it a platform capability

Use these questions as an operating-model review, not as a shopping list of tools:

  • Consumption: Are the supported inputs, outputs, defaults, and owner explicit?
  • Change: Is every target reached through reviewed, auditable evidence?
  • Security: Are identity and fail-closed guardrails part of every authorized path?
  • Operation: Does telemetry reach a named owner with a defined response?
  • Recovery: Are drift, restore, and teardown exercised rather than assumed?
  • Economics: Is cost ownership visible, and is there a tested exit path?

When those answers remain implicit, Terraform has not failed. The operating model is simply unfinished.

What the evidence proves—and what it does not

Azure-observed

Keyless state backend, private container, scoped data-plane role, versioning, seven-day retention, successful Terragrunt backend initialization, and bootstrap no-change convergence.

Authenticated-plan observed

The direct path proposed 10 secure-core resources. The platform path proposed 14 resources and the explicit observability, recovery, and deletion-protection capability delta.

Not yet lifecycle-observed

Workload apply, post-apply no-change plans, live diagnostic and lock queries, two-phase platform teardown, direct-path destroy, and final backend cleanup.

This distinction is deliberate. A passing local test proves configuration behavior. An authenticated plan proves provider-backed evaluation against a target. Neither is the same as observing a successful apply, operation, recovery exercise, and destroy.

Judge the delivery system, not the tool

The direct path and the platform path both use Terraform; the platform path also uses Terragrunt. Maturity becomes visible in the operational questions:

  • Can a team consume the capability without opening a bespoke ticket?
  • Can reviewers see the exact change before it is applied?
  • Do unsafe production configurations stop rather than warn?
  • Are health, recovery, drift, and ownership part of the contract?
  • Can the platform improve through feedback from real operation?
Terraform does not make you DevOps. It makes your engineering decisions executable—and exposes whether an operating model exists behind them.

Evaluate the path a change travels: who proposes it, what evidence is produced, who approves it, who observes the result, and how feedback changes the next version. If those responsibilities remain implicit or live in one engineer’s memory, adding Terraform, Terragrunt, or YAML does not supply the missing system.

Code and reproducibility

The complete Terraform module, direct root, Terragrunt configuration, native tests, security suppressions with rationale, and human-executed Azure runbook are available in the Terraform Does Not Make You DevOps lab repository.

The implementation is pinned to Terraform 1.14.7, Terragrunt 1.0.4, AzureRM 4.81.0, and Random 3.9.0. The recorded validation run included six native Terraform test runs, eight repository-contract tests, strict Terragrunt input validation, and ShellCheck. Gitleaks reported no leaks; Checkov reported 18 passed checks, no failures, and six documented skips; Trivy reported no unsuppressed high- or critical-severity findings. The sanitized validation summary records the scope and limitations.

The lab is disposable, not free. Because the workload resources were not applied for a measured interval, this article does not publish a dollar estimate. Estimate region-specific cost in the Azure Pricing Calculator before applying it, and follow the reviewed teardown procedure when finished. Expiry tags make ownership visible; they do not delete resources automatically.
